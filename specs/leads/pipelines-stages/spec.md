# Pipelines and stages
**SRS section:** 5.2 · **Requirement IDs:** LD-P1, LD-P2, LD-P3, LD-P4, LD-P5 · **Priority:** Must 4, Should 1 · **Feature flag:** crm_enabled
**Project:** crm_main_panel (Tenant Panel UI) · **Other side:** [crm_backend](../../../../crm_backend/specs/leads/pipelines-stages/spec.md)
**Overall status in this project:** ✅ (5 of 5 requirements implemented)

## Summary
The ordered stages a lead moves through. The Leads toolbar has a pipeline selector with a pencil beside it, and the pencil opens one dialog for both pipelines and their stages. The board, list, analytics, export and bulk actions all read the selected pipeline, which is remembered per member between visits. A won or lost stage is badged wherever a lead's stage is shown, and a stage marked "require a reason" prompts for one before the move is sent. Used by Tenant Admin, Sales Manager.

## Decisions
### Pipelines in the Tenant Panel (LD-P1 to LD-P5, 2026-11-25)
Decided by Raj. Change only through `/sdd-change`.

- **One board at a time.** `activePipelineId` is part of the screen's `filters`, so the list, the board, analytics, the export and any bulk action over "everything matching" all read the same pipeline. A list mixing pipelines would show columns from several boards.
- **The selector is the toolbar's first control,** in the same row as the filters and ahead of them, because it decides what every control after it is working on: the stages, the filters, the list, the board and the export all belong to the pipeline chosen there. It is separated from the filters by a vertical rule, and labelled "Pipeline", so it does not read as another filter. It is the one control in that row that stays on the Analytics tab, which has no filters, because those figures are per pipeline too.
- **The selector hides itself when there is nothing to choose.** With one pipeline it is the board's name in plain text with a "Default" badge; the dropdown appears at two or more. The pencil stays either way, because creating the first extra pipeline is what it is for, and it carries a tooltip since an icon alone says nothing. With no pipelines at all — only reachable if the pipelines request failed — the pencil becomes a labelled "Set up pipelines" button, so a member with permission still has a way in.
- **The pencil needs `leads.pipeline.manage`;** reading the pipelines needs only `leads.view`, matching the API. Without the permission the dialog is not rendered at all, and every control inside it is gated again on the same key.
- **Picking a board is not filtering.** `pipeline_id` is left out of `hasFilters`, so an empty board offers "add a lead" rather than "clear filters" — the same rule the API applies in `filtersApplied`.
- **Switching board clears the stage filter and the selection,** and starts at page 1: a stage filter naming the old board's stage would match nothing, and a selection of leads from the old board cannot be acted on from the new one.
- **The last board is remembered per member** in `localStorage` (`lib/leads/last-pipeline.ts`, key `orbitops.leads.pipeline.<userId>`), keyed by member because two people share a browser. The stored id is only used while it is still in the API's list, so a removed or renamed board falls back to the default. Storage failures (private browsing, blocking extensions) are swallowed: the default board is a fine answer.
- **Leads are not fetched until the board is known,** or the first page would be the default pipeline's and then be replaced a moment later by the remembered one's. If the pipelines request itself fails, the list loads anyway and the API answers for the default board — better than a blank screen.
- **The placeholder stage list is deleted.** `lib/leads/fallback-data.ts` is gone. It existed because organizations had no seeded stages and its ids were not real, so submitting with one selected always failed. Every organization now has a pipeline with stages, and a pipeline that genuinely has none says so and points at the pencil instead of offering six stages that do not exist.
- **One dialog for both.** Pipelines list on the left, the selected pipeline's stages on the right. The dialog reads the selected pipeline's stages into its own state rather than the slice's, so editing a different pipeline cannot swap the board out from under the screen behind it.
- **Reorder is up/down buttons,** not drag: two `sort_order` patches that swap the pair. Drag inside a dialog that already hosts a drag-and-drop board behind it is more trouble than it is worth, and the SRS asks only that stages can be reordered.
- **Stage colour is a native colour input plus the six presets the backend seeds with.** Those hex values are stage data saved to the server, not styling for the component, so they are literal values rather than theme tokens.
- **Outcome is one choice, not two switches:** "Stays open", "Closes as won", "Closes as lost", sent as the `is_won`/`is_lost` pair. A stage cannot be both.
- **Removing a pipeline:** the button is disabled with a tooltip when it is the organization's only one (known locally). "Still has leads" is only known from the API, so a 409 `PIPELINE_IN_USE` is shown in plain words. Removing the board the screen is showing clears the selection so the default is picked again, rather than leaving the member on a board that no longer exists.
- **Removing a stage offers to move its leads first.** The backend refuses while leads remain and sends no code for it, so a plain 400 with no code is taken as that. The member then picks another stage; the count is read first (a "move everything matching" is only accepted with the number the caller was shown), the leads are moved, then the stage is removed. A stage that requires a reason is not offered as the target, because the bulk endpoint cannot carry one. If the count comes back zero, the leads blocking the delete are outside the member's record scope and the message says to ask someone with wider access.
- **Every stage change goes through one function.** `moveLeadToStage` is used by the kanban drag and by the lead form, so the reason rule is asked about once and in one place. It prompts before the request when the stage has `requiresReason`, and if the API still answers `REASON_REQUIRED` (the rule was turned on while the screen was open) the same prompt opens rather than a toast the member can do nothing about. Cancelling drops the move and anything that was queued behind it.
- **The lead form sends no `pipeline_id` on edit.** A board change is not something that form does, and a `pipeline_id` sent without a stage from that board is refused by the API. On create it sends the board being shown, whose stages are the only ones the picker offers.
- **A bulk stage change leaves out stages that require a reason,** because one reason cannot speak for a whole batch and the API refuses it.
- **Error codes in plain words** in `lib/auth/errors.ts`: `PIPELINE_IN_USE`, `LAST_PIPELINE`, `PIPELINE_NAME_TAKEN`, `STAGE_NOT_IN_PIPELINE`, `REASON_REQUIRED`. The screen never shows the server's own message text.
- **Won and lost are a label, not a lock.** The badge appears on the board column, the list's Stage cell and the detail sheet, and nothing is disabled on a closed lead: the backend has no edit lock and a lead can be moved back out.

## Out-of-SRS behaviour
- "Move its leads, then remove the stage" is not in the SRS. LD-P2 says a stage may be deleted "after moving its leads" but not how; doing it from the same dialog saves the member a trip to the list and a hand-built bulk action.
- Remembering the last-used pipeline is not in the SRS. It was asked for alongside this work so returning to Leads does not jump back to the default board.
