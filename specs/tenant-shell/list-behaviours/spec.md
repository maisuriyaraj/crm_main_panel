# Common list behaviours
**SRS section:** 4.3 · **Requirement IDs:** SH-L1, SH-L2, SH-L3, SH-L4, SH-L5, SH-L6, SH-L7, SH-L8 · **Priority:** Must 7, Should 1 · **Feature flag:** None
**Project:** crm_main_panel (Tenant Panel UI) · **Other side:** [crm_backend](../../../../crm_backend/specs/tenant-shell/list-behaviours/spec.md)
**Overall status in this project:** 🟢 (7 of 8 requirements implemented)

## Summary
Sorting, paging, columns, saved views, selection and export that every list shares. Since 2026-11-24 there is one shared list surface, `components/shared/server-list.tsx`, driven entirely by the API's list contract, with `hooks/useServerList.ts` holding the page, page size, sort, column choices, saved views and selection. Leads and Contacts both run on it. `components/ui/data-table.tsx` stays for the small client-side tables (team members, invitations, roles).

## Design
- **Screens affected:** Leads (`app/[orgnization]/leads/page.tsx`), Contacts (`app/[orgnization]/contacts/page.tsx`).
- **New shared components:** `components/shared/server-list.tsx` (the list surface), `components/shared/column-chooser.tsx`, `components/shared/saved-views-bar.tsx`, `components/shared/field-help.tsx`.
- **Reused:** `components/ui/table`, `pagination`, `select`, `checkbox`, `popover`, `dropdown-menu`, `dialog`, `alert-dialog`, `tooltip`, `scroll-area`, and `pageWindow` from `components/ui/data-table.tsx` (now exported, so both pagers paint the same window of page numbers).
- **Tokens:** semantic tokens only — `border-border`, `bg-muted/40`, `text-muted-foreground`; no new colours.
- **Responsive:** the toolbar, selection bar and pager all wrap; the per-page selector and count sit on one line and fall to the next on a narrow screen.

## Decisions
1. **A new component rather than another mode on `DataTable`.** `DataTable` already carries a client-side search, sort and pager plus a `manual` escape hatch; adding columns, saved views and a two-mode selection on top of that would have made one component serve two different jobs. `ServerList` does only the server-driven job, and `DataTable` keeps the small local tables it already serves.
2. **Column keys are the API's keys.** A column declares the same key the API's column catalog uses (`full_name`, `assignee`, `lead_score`), so a stored column choice and a saved view mean the same thing on both sides. A key the API knows but a screen cannot render (`source` on Leads, which the client has no field for) is simply not offered in the chooser.
3. **Filters stay with the screen.** Only the screen knows what its filter bar looks like, so it owns that state and hands the values — already in the API's own query names — to `useServerList`, which turns them into the list query, the bulk payload and the export query. Applying a saved view calls back into the screen to put the view's filters into its controls.
4. **"All matching" is never implied.** Ticking the header box takes this page, exactly as many rows as the member can see. Reaching further is a separate button that names the number, and it only appears when there are rows beyond the page or a filter that defines "matching".
5. **`COUNT_CHANGED` reloads rather than retries.** The server changed nothing, so the screen reloads the list, drops the selection and says so; running it again is the member's call, with the real count in front of them. The API's error body carries no machine-readable count today, so the refreshed `pagination.total` is what the member is shown.
6. **The empty state's words and the ⓘ copy come from the API.** Both are served (`empty_state` on the list, `help` and `field_help` on the preferences), so the three empty cases are told apart the same way on every list, the create button follows the API's own `can_create`, and a field is explained with the same sentence in the table, the chooser and the form. `lib/lists/help-text.ts` is a fallback for the first render and is read only through `hooks/useFieldHelp.ts`.
7. **The Leads board and analytics read one page of 100.** They used to ask for 1000 rows, which the API now refuses. They ask for the largest page the contract allows and say plainly when there is more. Proper paging for the board (load more per column) is LD-V2 work, not part of SH-L*.

## API Changes
None in this project. It consumes `GET`/`PUT /app/list-preferences/:listKey` and the `/app/saved-views` routes, the `per_page` / `from` / `to` / `has_any_without_filters` fields on the two list endpoints, `scope: 'all_matching'` on the bulk endpoints, and `format` / `ids` on the export endpoints. All of them are described in the [backend spec](../../../../crm_backend/specs/tenant-shell/list-behaviours/spec.md).

## Risks
- **The page-size change is breaking on both sides.** This panel must ship with or after the API: an older build asking for `limit=1000` (Leads) or `limit=20` (Contacts) now gets a 400 with `INVALID_PER_PAGE`.
- **"Select all matching" on a destructive action.** The delete dialog says it covers every matching record including other pages, and the API caps it at 5,000, but nothing stops a member from confirming it over a wide filter.
- **The default saved view applies once per mount.** If a member sets a default and then changes filters by hand, the default is not re-applied — intended, but it means a saved view and the filter bar can disagree until the view is picked again.
- **Needs manual checking:** the column chooser's order surviving a reload, a shared view appearing for a second member, a `COUNT_CHANGED` race (change a record in another tab between the count and the action), and that the .xlsx file opens in Excel.

## Implementation Notes
- 2026-11-24: built the shared list surface and migrated both lists. No tests were written or run, at the requester's instruction, and `tsc` and `eslint` were not run either; the changed files were parse-checked only.
- `lib/leads/types.ts` and its mapper gained `firstName`, `lastName`, `alternateMobile` and `expectedBudget`, which the API already returned but no screen showed; the column chooser can now offer them.
- `ContactsPagination` is gone from `lib/contacts/types.ts`; both slices now hold the shared `ListPagination`.
- `ExportButton` is a menu rather than a single button, and its `fileName` prop no longer carries an extension (the format adds one, and the server's own file name wins).
- Later the same day, SH-L6 and SH-L8 were moved onto the API: the empty state reads `empty_state`, and the ⓘ copy reads `field_help` through `hooks/useFieldHelp.ts`, with `lib/lists/help-text.ts` kept only as the first-render fallback.
