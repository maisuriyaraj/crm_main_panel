# Tenant roles and permissions
**SRS section:** 2.2 · **Requirement IDs:** SH-R1, SH-R2, SH-R3, SH-R4 · **Priority:** Must 3, Should 1 · **Feature flag:** None
**Project:** crm_main_panel (Tenant Panel UI) · **Other side:** [crm_backend](../../../../crm_backend/specs/tenant-shell/tenant-rbac/spec.md)
**Overall status in this project:** ✅ (4 of 4 requirements implemented)

## Summary
Controls what each tenant user can do by module and action. The role editor shows whatever permission catalog the API sends, and every screen gates on the effective permissions from `/auth/me`, so a module switched off for the organization disappears for everyone. Leads and Contacts have CSV export buttons. The role editor sets each role's record scope (Own, Team, All), the Leads list filters by "My leads / My team's leads / All leads" within it, and assignee pickers offer only people the member may assign to. Used by Tenant Admin and every tenant role.

## Decisions (2026-11-10)
- **Exports** go through `downloadExport` in `lib/exports.ts` (shared Axios client, `responseType: "blob"`). Only filters that are set are sent. On Leads: search, stage (real ids only, not placeholder stages), owner, priority and temperature. On Contacts: search and owner. The server search on Leads also matches mobile numbers, which the on-screen search does not, so the file can hold slightly more rows than the list shows. A failed download's JSON body is read back from the blob so its code gets plain words (`EXPORT_TOO_LARGE`: "more than 10,000 rows, narrow the filters").
- **Module off vs no access:** `NoAccess` takes the catalog `module`. When `/auth/me` lists it in `disabledModules`, the message names the plan or the subscription, not the member's role. The reason never says whether a plan or an override decided, matching the API.
- **Reserved role names:** the role form refuses the five SRS role names as well as the original four, as the API does.
- **Plain words** (`lib/auth/errors.ts`): `PERMISSION_NOT_DELEGABLE`, `PERMISSION_DEPENDENCY`, `ROLE_NOT_ASSIGNABLE`, `ROLE_NAME_TAKEN`, `INVALID_ROLE`, `LAST_OWNER`, `OUT_OF_SCOPE`, `EXPORT_TOO_LARGE`; `FEATURE_DISABLED` now reads "This module isn't available on your plan." Team screens still show the API's own message for team codes (it is already plain English); the export uses this map.

## Decisions (Part B, 2026-11-10): record scope
- **Role editor:** under the matrix, "Which records they see" shows a choice for each of Leads and Contacts whose View permission is ticked: Own ("Only leads assigned to them, or that they created and nobody is assigned to"), Team ("...assigned to anyone in their team. Without a team, the same as Own"), All. A new role starts at Own, as the API does; a duplicate keeps the source role's scopes. Changing only a scope counts as an unsaved change and saves.
- **Ownership filter on Leads:** from `/auth/me` `scopes.leads` and `teamId`. All scope: All leads, My team's leads (only with a team), My leads; Team scope: My team's leads, My leads; Own: no choice, "Showing your leads". Sent as `owner=all|team|self`; the API never widens it. The export sends the same filter.
- **Server-side list:** search (debounced), stage, owner, priority, temperature, ownership and sort go to `GET /leads`; the list pages 25 at a time. Sorting is offered on name, priority, temperature, score and value (what the API can sort); stage and owner are no longer sortable. "Select all" now selects the current page, and changing a filter or page clears the selection.
- **Assignee pickers** (lead form, bulk "Assign to", contact form, bulk "Reassign to") list only options with `assignable.leads` / `assignable.contacts`. When editing a record whose current owner is outside that list, the owner is still shown so the form displays it; the API checks only a change.
- **Errors:** lead actions show `OUT_OF_SCOPE` and other known codes through `apiErrorMessage`; Contacts shows the API's own message, which is already plain ("You can only assign records to yourself.").
